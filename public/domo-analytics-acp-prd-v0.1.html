Analytics Data Platform & ACP
A shared Postgres data platform for Domo Cafe — Toast Analytics API + other 3rd-party sources flow in through one owned pipeline, and a secure Agent Communication/access Protocol (ACP) lets other Jarvis agents read it without ever touching raw credentials.
01
Overview
Executive Summary

Izzy's ask, verbatim (2026-07-13): review the Toast Analytics API data fields, apply a smart DB schema, and — because that database will be shared by other agents going forward — design a protocol so other agents can securely access this data. This document is that design.

Two things are being solved together because they're the same system: (a) a real, reviewed schema for the Toast Analytics API (menu, metrics, labor, check, payout, guest, restaurant-info) that extends the existing ToastDailySnapshot Postgres database, and (b) an access protocol — the Domo Data ACP — that lets any future agent (Staff OS, Merch Portal, a finance agent, etc.) read this data over HTTP with a scoped API key, instead of every new agent getting its own copy of the Postgres connection string.

Design Principle

I own ingestion. No other agent talks to Toast, and no other agent gets the raw DATABASE_URL. Every other agent talks to one HTTP API, gets exactly the fields its scope allows, and every access is logged. This is the same shape as the existing /api/jarvis/status pattern already used across the stack — just formalized and extended to real data reads, not just health checks.

🍞
One Owner
Toast Analytics + 3rd-party ingestion lives in one pipeline (this account), never duplicated per-agent
🔐
Scoped Keys
Each consuming agent gets its own API key tied to exactly the data it's allowed to see
📜
Logged Access
Every read is logged with agent identity, endpoint, and timestamp — auditable, revocable

Refined Data Schema

A raw-SQL draft schema (toast-analytics-api-schema-v0.1.sql) was already written 2026-07-10 for four of the seven report families. Reviewed against the actual live credential + Toast's overview docs — the shape holds up. Refinements for v0.1 of this PRD:

  • Port to Prisma, not raw SQL. geopulse-ai/prisma/schema.prisma is the existing home for ToastDailySnapshot/ToastSyncLog. Adding Prisma models (not a hand-run .sql file) keeps one schema-of-record and lets prisma db push apply it the same way every other Domo table has been applied.
  • Add Payout Reporting as a sixth table (ToastPayoutReport) — missing from the v0.1 SQL draft, needed for bank-deposit reconciliation.
  • Skip Guest Reporting for now — no CRM/loyalty use case exists yet; revisit if a loyalty program is ever built.
  • Confirm-on-first-pull columns: the draft's ToastCheckReport carries a rawPayload JSONB fallback column specifically because its exact field list wasn't docs-confirmed when written — keep that safety net for the first real sync, then tighten typed columns once verified.
  • Keep the already-designed ToastMerchSkuMap support table — it's the missing link between Toast's flat menu-item list and Domo's licensed-vs-house-merch royalty math, and directly feeds the Merch Portal PRD's sell-through reporting.

Ingestion
Sync Pipeline

Mirrors the existing toast-sync.mjs / toast-sync-today.mjs pattern already proven for Orders API data — same repo, same credential-file convention, same idempotent-upsert shape.

  1. scripts/toast-analytics-sync.mjs — new script, reads storage/credentials/toast-analytics-api.json, authenticates against the Analytics API's own auth endpoint (separate token from Standard API), pulls each report family for a date range, upserts into the six models above, writes a row to ToastAnalyticsSyncLog per report per run.
  2. Historical backfill: opening date (2026-06-13) → yesterday, run once.
  3. Daily/ongoing: cron-style scheduled run (same cadence as the existing Orders sync) for the closed prior day, plus a same-day partial-sync variant for live dashboards, matching the day/day-partial split already established.
  4. Idempotency via the unique constraints already designed (business date + dimension) — safe to re-run without duplicating rows, same pattern as ToastDailySnapshot.

Ingestion
Other 3rd-Party Sources — Same Pipeline, Same Owner

Izzy's ask explicitly includes "Toast and other 3rd party sources" — the architecture is designed so any future source plugs into the same shape, not a one-off integration per source:

  • One sync-script-per-source convention (scripts/<source>-sync.mjs), each writing to its own clearly-namespaced tables (Toast*, future Square*, Instagram*, etc.) in the same shared Postgres DB.
  • One sync-log table per source (ToastAnalyticsSyncLog today) — consistent shape so a future "data health" dashboard can query sync status across every source the same way.
  • Credentials always in storage/credentials/<source>-api.json (established convention) — never inline in scripts, never committed to git.
  • This account (Domo bot) remains the single ingestion owner for all Domo Cafe 3rd-party data. Other agents never get source credentials — they get the ACP described below.
06
Multi-Agent Access
The Problem

Once Staff OS, Merch Portal, a future finance/reporting agent, and others all want this data, the naive path is copying the Postgres DATABASE_URL into every new app's environment variables. That's the wrong pattern for four reasons:

🔓
Credential Sprawl
Every new agent/app is another place the DB password can leak, get logged, or get committed by accident
🧨
No Blast Radius Control
Raw DB access means any agent can read (or write) any table — no way to give an agent "labor data only"
🕵️
No Audit Trail
Postgres connection logs don't tell you which agent read what, when, or why
🔗
Schema Coupling
Every consumer that queries Postgres directly breaks the moment a column is renamed or a table is refactored

The fix: consuming agents talk to an HTTP API, never the database directly. This is already the exact pattern used by /api/jarvis/status across every Jarvis-integrated app (per the mandatory Jarvis API Build Standard) — this PRD formalizes and extends it into a real data-access layer, not just a status check.

07
Multi-Agent Access
ACP Design — Domo Data Access Protocol

ACP = Agent (Data) Communication Protocol. One HTTP API, hosted in geopulse-ai alongside the existing /api/domo/* routes, that any authorized agent calls to read Domo data. No agent — human-built app or AI agent — ever receives the Postgres connection string.

Endpoint shape

GET  /api/acp/v1/health                    → {"ok": true, "sources": ["toast"]}
GET  /api/acp/v1/metrics/daily?from=&to=    → ToastMetricsReport rows
GET  /api/acp/v1/menu/top-sellers?from=&to=&limit=
GET  /api/acp/v1/labor/summary?from=&to=&groupBy=employee|job
GET  /api/acp/v1/checks?date=
GET  /api/acp/v1/merch/sell-through?from=&to=
POST /api/acp/v1/query   { "model": "ToastMetricsReport", "where": {...}, "select": [...] }
                             ↳ generic, scope-checked, whitelisted-model-only escape hatch

Every route: (1) validates the caller's API key, (2) checks the key's scope against the requested model/fields, (3) executes a read-only Prisma query, (4) writes one row to AcpAccessLog, (5) returns JSON. No route ever accepts arbitrary SQL. The generic /query escape hatch is model-whitelisted (Prisma model name + allowed field list per scope) — never a raw SQL passthrough.

Why HTTP, not a shared Prisma client / package

A tempting shortcut is publishing the Prisma schema as a shared npm package so other apps import the same client. Rejected: that still hands out full read/write DB credentials to every consumer, and doesn't give per-agent scoping or an audit trail. HTTP + scoped keys is slightly more code up front and is the only version of this that's actually secure.

Multi-Agent Access
Auth & Permissions
ModelDesign
Authx-api-key header, same convention as JARVIS_API_KEY. Each consuming agent gets its own key — never a shared master key across agents (the master JARVIS_API_KEY remains for the existing /api/jarvis/status health-check pattern only, kept separate from ACP data-read keys).
ScopesEach key row stores an allowed model + field list, e.g. {"models": ["ToastLaborReport"], "fields": ["*"]} for a future Staff OS key, or {"models": ["ToastMenuReport","ToastMerchSkuMap"], "fields": ["*"]} for Merch Portal. A key with no matching scope for a requested model gets 403, not a silent empty result.
New tableAcpApiKey — id, key (hashed), label (agent name), scopes (JSON), active, createdAt, revokedAt, lastUsedAt.
New tableAcpAccessLog — id, apiKeyId, endpoint, model, paramsJson, statusCode, rowsReturned, calledAt. This is the audit trail — answers "who read what, when" for any future security review.
RevocationSet active=false or revokedAt on the key row — takes effect immediately, no redeploy needed since the check happens per-request.
Rate limitingSimple per-key request counter (reuse whatever pattern, if any, protects /api/jarvis/status today; otherwise a basic sliding-window check) — prevents a misbehaving agent loop from hammering Postgres.
Write accessOut of scope for v0.1. ACP is read-only. If a future agent needs to write (e.g. update ToastMerchSkuMap classifications), that's a separate, explicitly-scoped write endpoint added later — not bundled into the generic query route.
Bot Delegation Rule, Applied to Agents Too

This mirrors the existing human-facing rule in AGENTS.md — business bots operate in their own lane and relay rather than take over each other's work. The ACP is the technical enforcement of the same idea for agent-to-agent data access: an agent gets exactly the scope it needs for its lane, nothing more, and every cross-lane read is visible in the log.

Reference Implementation — First Consumer

The Domo Staff OS PRD (v0.1, 2026-07-11) already calls for a Toast clock-in/out reconciliation feature and a labor-% guardrail. That becomes the first real ACP consumer: once domo-scheduler is deployed, it gets one scoped key ({"models": ["ToastLaborReport"]}) and calls GET /api/acp/v1/labor/summary instead of ever holding a Postgres credential of its own. This validates the protocol end-to-end on a real, already-planned feature rather than shipping ACP as an unused abstraction.

Open Questions
Q1
Which agents need access first, and to what scope?
Staff OS (labor data) is the clear first consumer per its own PRD. Merch Portal (menu/SKU data) is the likely second. Confirm before cutting real keys — scopes should be requested per-agent, not pre-issued broadly.
Q2
Does the ACP live in geopulse-ai or move with the eventual "database moving to sps" migration noted in earlier memory (2026-06-30, still parked/open)?
Recommend building it in geopulse-ai now (where the data already lives) and carrying the ACP routes forward unchanged if/when that migration happens — the HTTP contract is what matters to consumers, not which repo serves it.
Q3
Should non-agent consumers (e.g. a future investor-facing dashboard) use the same ACP, or a separate public-facing API?
Recommend separate. ACP is agent-to-agent, internal, and assumes a trusted-but-scoped caller. Anything investor/public-facing should go through its own gated layer (same pattern as the EZLiving/SPS investor portals), not directly through ACP keys.
Q4
Formal Prisma migration vs. db push?
Memory flags this as recurring debt (riderFarePerTrip columns, cash/creditRev columns all went in via db push with no migration file). Recommend generating a real migration for this batch of new tables since it's a bigger schema change than a nullable column add — cleaner history going forward.
