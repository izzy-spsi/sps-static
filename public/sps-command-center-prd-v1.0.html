01

Overview

The current Jarvis HQ Dashboard (izzy-spsi.github.io/jarvis-dashboard) is a single static HTML page — a curated list of project links and version badges. It has served well as a project directory, but Izzy has outgrown it: it can't hold structured data, has no login/security, and has no concept of "a company's stuff lives here."

This PRD defines its replacement: the SPS Command Center — one secure home base, gated by two-factor authentication, with a dedicated Command Center underneath it for every company SPS manages. Each company Command Center follows the same 5-section template (Resources, Business, Investment, Marketing, Operations), so the system stays consistent and predictable no matter how many companies get added.

🔐
One secure entrance
2FA at the root, trusted-device bypass for known devices, full 2FA required everywhere else.
🏢
One command center per company
Domo Cafe, Flywheel, EZLiving, Blue Highway, Family — each fully organized, each with its own identity.
🧱
Same shell, different content
Resources / Business / Investment / Marketing / Operations repeat everywhere — Operations content differs per company.
➕
Built to grow
New companies are a config entry, not a rebuild — the architecture is designed for this from day one.

Problem Statement

Izzy's words: "I've outgrown it."

The Jarvis HQ Dashboard was built as a link directory (project cards + version badges). It cannot hold real structured data — proforma numbers, NDA status, unit costs, task lists — it can only point at other tools that hold that data. As the number of ventures and the depth of tracking needed has grown, the dashboard has stopped being a "command center" in any real sense.

03

Architecture

One root shell, gated by 2FA, containing a tile per company. Each company opens into the same 5-section template.

🔐 SPS Command Center (root — 2FA gated) ├── 🥐 Domo Cafe ├── 🚕 Flywheel ├── 🏙️ EZLiving ├── 🚤 Blue Highway ├── 👨‍👩‍👧‍👦 Family └── (future companies added via config — see Section 07) Inside each company: ├── 📦 Resources — tech stack, tools, vendors, partnerships ├── 📊 Business — BI data, proforma, unit costs, revenue model ├── 💰 Investment — plan, raise, valuation, pitch deck, notes, NDAs ├── 📣 Marketing — site, social, events, costs, run-of-show, collabs └── ⚙️ Operations — automation, training, HR, scheduling (differs per company)
Key design decision: companies are data, not code

Instead of hand-building 5 pages per company, there is one generic Company Command Center template driven by a companies config (name, slug, brand colors/logo, which sections are enabled). This is what makes new companies cheap to add — see Section 07.

04

Security & Auth

Requirements (from Izzy)
  • The root Command Center must be secured — 2FA required.
  • Trusted devices (laptop, phone, desktop) get a persistent key/token so they skip full 2FA on every visit.
  • Any other device/method must still complete full 2FA — no backdoor around it.
  • Once authenticated at the root, no re-authentication is required to move between company command centers (single session covers everything underneath).
Proposed Implementation
PieceApproach
2FA methodTOTP (Google Authenticator / 1Password-style authenticator app) — no SMS costs, works offline, industry standard
Trusted deviceSigned long-lived token/cookie issued per device after first full 2FA pass ("remember this device" pattern, e.g. 30–90 day expiry, revocable)
Untrusted accessAny login without a valid trusted-device token always requires the full TOTP challenge
Session scopeOne root session token grants access to all company command centers underneath — no per-company re-auth
RevocationAdmin control to revoke a specific trusted device (e.g. lost phone) without resetting 2FA entirely

Company Sections (the 5-part template)

Build this section as a flexible content area (arrangeable structured blocks/widgets), not a fixed form, so it can hold genuinely different content types without a separate code path per company.

07

Adding New Companies (Scalability)

Answer to Izzy's question: "Will this architecture allow me to add new companies?"

Yes — by design. Companies are config, not hardcoded pages. Adding a new company is meant to be an admin action, not a development project (for the standard case).

What adding a company looks like
  1. Add a row to the company config: name, slug, logo, brand accent color, which of the 5 sections are enabled.
  2. It automatically appears as a tile on the root dashboard.
  3. All 5 section pages exist immediately, empty and ready to populate — no new code, no redeploy.
What stays free (no extra engineering per company)
  • Branding — logo/accent/theme pulled from the config row (Domo's brown/cream vs. Flywheel's red/dark just works).
  • Section toggling — a company that doesn't need "Marketing" yet can hide that tab without deleting anything.
  • Operations flexibility — built as arrangeable content blocks, so Family's todos/school-stuff and Flywheel's dispatch ops both fit the same section type.
What still needs real engineering (expected, not a flaw)

Any bespoke live data integration — e.g. Domo's Toast POS sync — is genuine per-integration work regardless of architecture. The shell scales for free; real pipelines still take real build time. New company = config action. New data source = a small scoped engineering task.

Task List & Phasing

PHASE 0 Foundation — nothing else works without this Not Started
  • Stand up the app (Next.js + Postgres) — this becomes the root shell
  • 2FA login (TOTP)
  • Trusted-device mechanic (remember device 30–90 days, full 2FA otherwise)
  • Session-wide SSO — root auth covers every company command center underneath
  • Company config schema — companies are data, not hardcoded pages (see Section 07)
PHASE 1 Shell & Navigation Planned
  • Root landing page: company tiles (Domo Cafe, Flywheel, EZLiving, Blue Highway, Family, + SPS itself if in scope)
  • Generic Company Command Center template — 5 sections as tabs/sidebar
  • Per-company branding pulled from config (Domo brown/cream, Flywheel red/dark, etc.)
PHASE 2 Populate One Company End-to-End (Template Company) Planned [ Recommend: Domo Cafe ]
  • Resources — tech stack + partnerships
  • Business — wire in existing live Toast/Proforma data (real numbers, not placeholders)
  • Investment — link/embed existing docs (KISS notes, NDAs, decks)
  • Marketing — costs, run-of-show, collabs (manual entry to start)
  • Operations — build Domo's version first as the working pattern; do not assume it generalizes as-is to other companies
PHASE 3 Replicate to Remaining Companies Future
  • Flywheel, EZLiving, Blue Highway, Family — same shell, populate with what already exists in memory/Notion/decks first
  • Flag real content gaps per company after initial population, not before
PHASE 4 Polish Future
  • Global search across all companies/sections
  • Mobile responsiveness (apply patterns already proven on SPS + EZLiving this week)
  • Root-level alerts/notifications (e.g. "EZLiving has 2 pending NDAs")

Status: Planning only. Per Izzy's instruction, no build has started. This document is for review/prioritization before any Phase 0 work begins.
